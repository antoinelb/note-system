# Surround's pair set, scoping and padding

## Context

The vim friction batch (`docs/plans/2026-08-23-vim-friction-batch.md`, items 4–6) brings vim-surround's `cs`, `ds`, `ys` and visual `S` to the grammar. Item 4 lands the finder (`motions::surround_spans`) two tasks ahead of the keys that will call it, so the choices below are fixed now and simply consumed later.

## Decision

- **The pair set is `* _ ' " \` ( ) [ ] { } < > « »`** — the text objects' own set (`adr/2026-08-one-register-the-clipboard.md`), plus Typst's `*` and `_` emphasis markers, plus the French guillemets `«`/`»` that `object_kind` already maps for `di«`/`da«`. No new `ObjectKind` variant: `*` and `_` are `ObjectKind::Quote('*')` and `ObjectKind::Quote('_')`, and `«`/`»` are `ObjectKind::Pair('«', '»')`, exactly the kind `object_kind` already answers.
  `«` pads on wrap, matching both the opening-bracket rule (`« x »`) and French typography's own spacing inside guillemets; `»` is bare, as every closing key is.
- **Quote-like and bracket-like pairs keep the text objects' own scoping**: `*`, `_` and the quote characters pair left to right along the caret's line (`quote_delimiters`, factored out of `quote_object`); bracket pairs nest within the block, depth-counted (`bracket_delimiters`, factored out of `pair_object`). `surround_spans` dispatches on `ObjectKind` and calls whichever helper the kind already answers to — it does not re-implement either scan.
- **The finder returns both delimiter spans, not one collapsed range**: `cs` and `ds` replace or drop each delimiter independently — a bracket's opener and closer are different characters, and even a quote's identical two characters live at different offsets that must each be spliced on their own. A single `Range` covering the whole pair (as `object`'s `around` already gives) cannot address that.
- **Padding is a splicing-time rule, not a finder concern**: when *wrapping* new delimiters onto a target (`ys`, visual `S`), an opening bracket pads the content with a space on the inside (`( x )`), a closing one does not (`(x)`) — vim-surround's own asymmetry — and every other pair (quotes, `*`, `_`) is bare. `cs` writes its new delimiters bare in every case and never re-pads existing content; only a fresh wrap ever adds the space. `surround_spans` hands back bare offsets; the padding lives in the `ys`/`S` splice, not here.
- **Register behaviour follows the verb, not the finder**: `ds` and `cs` route the delimiters they remove to the clipboard exactly as `c` and `d` do for any other span (`adr/2026-08-one-register-the-clipboard.md`); `ys` and visual `S` add delimiters without deleting anything, so they leave the register untouched.
- **`ys` reuses `Operator::Yank` with a `wrapping` flag, not a new operator**: every existing motion, count and object path resolves the noun unchanged; only `finish_operator`, at the end, diverts to `Prefix::Wrap { span, record: true }` — waiting for the pair key — instead of yanking, when `wrapping` is armed. `Change::Wrap` carries its own `WrapNoun` (motion, object or lines), not a `Noun`: `Noun::Clusters` — the noun that belongs to `s` alone (`adr/2026-08-clusters-noun-belongs-to-s.md`) — has no `WrapNoun` variant, so the dot replay (`repeat_wrap`) cannot even be asked to resolve one; there is nothing left to refuse.
  `yss` is the linewise idiom, vim-surround's own doubled key: it runs `current_lines(Operator::Yank, view)`, the same span dd/cc/yy/Y already take, and records a `Change::Wrap { noun: WrapNoun::Lines, .. }`. `ysy` is nothing — vim-surround doubles the `s`, not the `y` — so a stray `y` behind an armed wrap aborts exactly as a mismatched pair of verbs does.
- **`Prefix::Wrap` carries a `record: bool`**: only the `ys` path (`record: true`) fills the pending `Change::Wrap`'s pair slot once the key lands, so a `viwS)` that follows a `ysiw(` cannot corrupt the still-open `ys` record — visual `S` always arms `record: false`.
- **Visual `S` shares `visual_span` with `visual_operate`**: it takes the exact same span the verbs (`d`/`c`/`y`) would over the same selection, so the verbs and `S` cannot drift apart on what "the selection" means. It still records no `Change`: `S` arms `Prefix::Wrap` directly rather than going through `object_noun`, and deliberately leaves `last_change` untouched — the dot after visual `S` replays whatever change preceded it, not the wrap.
  The mode stays `Mode::Visual` until the pair key resolves, then lands in normal either way, an unknown pair key included — flipping to normal a keystroke early would have redrawn the whole-line highlight charwise with no owner for that one frame.
- **The refactor changes no behaviour**: `quote_object` and `pair_object` now build their span from `quote_delimiters`/`bracket_delimiters`, but every existing object test (nesting, delimiter-standing, unmatched openers, cross-block, off-line quotes) passes unmodified.

## Rejected

- **A single collapsed span for the pair** — matches `object`'s `around` shape but cannot drive `cs`/`ds`, which touch each delimiter on its own; would force the surround keys to re-scan for the second delimiter anyway.
- **A new `ObjectKind::Emphasis` for `*`/`_`** — they pair exactly like a quote character (same character, left-to-right, chunked in twos); a new variant would duplicate `quote_delimiters` for no behavioural gain.
- **Padding decided inside the finder** — `surround_spans` is asked from three places (`cs`, `ds`, and indirectly by `ys`/`S` locating the wrap target) and only one of them ever pads; keeping the finder pad-agnostic keeps it a pure "where are the delimiters" answer.
- **Recording a `Change` for visual `S`** — would need to capture the exact selection extent to stay replayable, and no daily-writing need for repeating a wrap over a different visual selection has shown up; simpler to leave the dot as whatever change came before.
