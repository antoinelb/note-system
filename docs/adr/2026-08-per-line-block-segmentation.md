# Blocks are one per physical line; multi-line constructs and the preamble run merge honestly

**The rendering half is superseded by `adr/2026-08-cursor-split-rendering.md`**: fragments now compile as two cursor-split regions, not one per block; `blocks::segment` itself, and everything below about what a block *is*, stands unchanged.

## Context

`2026-07-block-segmentation-parbreak-tiling.md` cut blocks at top-level `Parbreak` nodes — a block was a maximal run of markup between blank lines, so a heading, a two-line list, or a paragraph all rode as one editable unit.
That paragraph granularity fought the hybrid editor's own vim layer: `dd` on one line of a two-line list deleted the *whole* list (the block was the only unit `ObjectKind::Block` could name), and the line the widget rendered as "the source" routinely spanned several unrelated visual lines glued only by the absence of a blank line between them.
The todo-fixes plan asked for line-level blocks directly: each line is its own editable unit, and a line that cannot compile alone — inside a raw fence, a multi-line `#let`, a multi-line `#table`, an unclosed construct — merges with its neighbours instead of breaking.

## Decision

- **A block is a physical line**, not a paragraph. `blocks::segment` walks `typst_syntax::parse(text).children()` as before, but now splits on every `'\n'` found *inside* a top-level `Space` or `Parbreak` child, rather than only at `Parbreak` boundaries. A `Space` child with no newline just advances the offset without moving `content_end`, exactly as it always excluded trailing spacing from a block's content.
- **The parse tree decides what merges, never character counting.** A raw fence, a multi-line `#let x = (…)`, a multi-line `#table(…)`, display math `$ … $`, an unclosed `#let x = (` — every one of these is a *single* top-level child in typst's own parse tree, so the newlines inside them are never top-level `Space`/`Parbreak` children and never trigger a split. This is the same tree the phase-2 never-regex rule already requires; counting unclosed `[`, `(`, `$` in raw source text would misfire on brackets inside strings, comments, raw fences, and math (where `$` is a parity toggle, not a delimiter, and a raw fence carries none of these characters at all).
- **The leading `#import`/`#show`/`#meta` run stays one preamble block.** While walking, each line-block records whether its own children include a `ModuleImport`, a `ShowRule`, or a `FuncCall` whose callee identifier is `meta` (read off the call's own AST node, not a string prefix — `#` arrives as a separate `Hash` child ahead of these, so the check is an OR over the line's children rather than "the first child"). Afterward, a leading run of 2 or more such lines folds into one block; a lone import with nothing preamble-shaped after it stays its own block (nothing to fold), and a blank line is not preamble-shaped, so it ends the run honestly rather than silently swallowing it.
- **The trailing zero-length block still exists**, unchanged in spirit from the parbreak version: the final unconditional push after the loop uses `text.len()` regardless of what the last split already consumed, so a note ending in `\n` gets a genuinely empty last block — the line the cursor rests on (`adr/2026-08-cursor-always-in-the-note.md`). A **fully blank note** (empty, or only blank lines) is special-cased before the walk: if every top-level child is `Space`/`Parbreak`, `segment` returns one block covering everything, matching the old behaviour rather than exploding every blank line into its own block.
- **Editor's "active block" is now effectively "active line."** Nothing in `Editor` changed to make this true — it already treated whatever `blocks::segment` handed it as the unit of editing — but the consequence is real: opening a note wakes its last block, which is now the trailing empty line rather than the note's last paragraph, and a vertical arrow key inside a single-line block has nothing to move to within the block, so it slides to the neighbouring block (or, while selecting, clamps to that line's own start) far more often than it used to.
- **`ip`/`ap` (`ObjectKind::Block`) now name a line, not a paragraph.** `motions::object`'s `Block` arm was already "read the block map, don't scan" — it didn't change — but what the block map now hands back is one line's content (`ip`) or that line plus its own separator (`ap`), matching vim's real `dd`/`yy` muscle memory far more closely than the old paragraph reading did.

## Known ceilings (accepted)

- **Fragment-compile and cache cost multiply, and the cost is real.** Every physical line is now its own `FragmentCache` entry and its own off-thread compile, where a five-line paragraph used to be one: one typst fragment and one ~17 KB SVG per physical line, measured at ~29 ms per compile out-of-process. No performance work went into this change — the cache's existing mark-and-sweep bound is the only ceiling in place — and a note with many short lines now compiles markedly more fragments than before. Accepted for now because nothing in the todo wording asked for it; revisit if it is felt.
- **Cross-block state crosses even less than before.** `2026-07-block-segmentation-parbreak-tiling.md`'s "cross-block state does not cross fragments" ceiling now bites inside what used to be one paragraph: a list's second item can no longer see a `#let` bound on its first line, because they are different blocks. This was already true across paragraphs; it is now also true within one.
- **A single-line binding used on the very next line is not merged.** `#let x = 3` on its own line, followed by `uses #x` on the next, opens and closes no `[`, `(`, or `$` across the two lines, so the parse tree reports them as separate top-level children and `segment` leaves them as two blocks; the second renders a `render-error` where the old paragraph tiling compiled them together. The todo wording scoped merging to lines that "cannot compile alone" by way of an unclosed `[`, `(`, or `$` — full cross-line dependency analysis (does this line's `#x` resolve without the one before it?) is exactly the character/identifier counting the never-regex rule forbids, so it stayed out.

## Rejected

- **Counting unclosed `[`, `(`, `$` in the raw line text**, the plan's own literal wording — rejected for the reasons above: it is exactly the character-counting the never-regex rule exists to prevent, and it cannot see past strings, comments, or raw fences to know whether a bracket is real syntax at all.
- **Keeping paragraph blocks and adding a separate "line cursor" for vim** — rejected because it would mean two disagreeing models of "the current editable unit," one for the mouse/widget and one for the modal grammar, undoing the "strict buffer/widget separation" the v2 vim layer was built to slot into cleanly.

Supersedes `2026-07-block-segmentation-parbreak-tiling.md`'s "Rejected" section, which ruled out line-based segmentation outright ("typst constructs span lines and only compile as complete expressions") — true of a naive line split, not of one that defers to the parse tree for exactly which lines a construct spans.
